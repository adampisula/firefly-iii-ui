# Exact Firefly III backend upgrade procedure

Backend compatibility changes are explicit product work. The currently supported version is exactly Firefly III 6.7.9; do not broaden it to a semver range or change the compatibility manifest to clear a failing check.

1. **Approve the target.** Record the requested exact backend version and identify an official release. Keep the original official image; backend code, database shortcuts, patches, extensions, plugins, and custom backend images are not allowed.
2. **Verify source and image provenance.** Inspect the matching upstream source/docs and official image release. Record source revision separately from the resolved image digest and architecture. A source commit or mutable tag does not prove image provenance. Resolve the digest and runtime `/api/v1/about` version only with an isolated environment; never invent a digest or use production for discovery.
3. **Pin the API specification.** Obtain the official spec for that exact release from documented upstream provenance. Record immutable revision, URL, SHA-256 and license in `plans/inventory/spec-provenance.json`. Do not substitute a neighboring release or treat the API docs site's current default as the target contract.
4. **Reconcile the contract.** Regenerate/diff normalized method/path declarations against both inventories, retaining aliases and adjacent OAuth/package routes as separate documented concerns. Review request/response fields, permissions, side effects, known source discrepancies, UI workflows, and all count/ID deltas. Preserve the 247/119 baseline records; additions require review, not deletion or renumbering.
5. **Update the coupled version contract together.** Coordinate changes to `backend-compatibility.json`, package version, release-tag pattern, runtime compatibility tests and deployment documentation. The frontend version prefix must match the exact supported backend version. Never add a silent compatibility bypass or speculative multi-version adapter.
6. **Run isolated verification.** Update source/spec drift checks and contract tests; use only a disposable official image with isolated volumes and local notification/webhook sinks. Verify `/api/v1/about` returns the exact target in `data.version`. Keep unknown/mismatched versions blocked. Do not run destructive, cron, purge, notification, or external-delivery checks against production.
7. **Record evidence and residuals.** Update task cards, inventory row states/dispositions/evidence, and release notes with commands, image digest, runtime response evidence, reviewed deltas, and remaining unsupported capabilities. `plans/VALIDATION.md` is planning validation, not runtime proof. Do not mark a workflow verified from source/spec comparison or mocked tests alone.

Until each exact-version source/spec/image gate is satisfied, the existing compatibility target remains authoritative and the newer backend is unsupported.
